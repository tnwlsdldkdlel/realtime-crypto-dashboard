## 1. 어댑터 패턴이란?

**어댑터 패턴(Adapter Pattern)**은 호환되지 않는 인터페이스를 가진 두 객체가 함께 동작할 수 있도록, **중간에서 변환해주는 래퍼(Wrapper)**를 만드는 구조적 디자인 패턴입니다.

> "110V 플러그를 220V 콘센트에 꽂기 위해 사용하는 **돼지코(변환 어댑터)**와 똑같습니다."

---

## 2. 왜 필요한가? (문제 상황)

### 상황: "API가 바뀌었어요!"

우리가 만든 앱은 `price`라는 필드를 사용하는데, 백엔드 API가 갑자기 `cost`로 필드명을 바꿨다고 가정해 봅시다.

**[나쁜 예: 앱 전체 수정]**
앱 전체에서 `price`를 쓰고 있는 100군데 코드를 전부 찾아서 `cost`로 바꿔야 합니다.
- 실수할 확률 매우 높음
- 유지보수 지옥

**[좋은 예: 어댑터 사용]**
API에서 데이터를 받아오는 **입구(Adapter)** 딱 한 곳만 수정하면 됩니다.
- 앱 내부 코드는 건드릴 필요 없음 (`price` 그대로 사용)
- 어댑터가 `cost`를 받아서 `price`로 바꿔서 넘겨줌

---

## 3. 핵심 원리

1.  **Client (우리 앱)**: 내가 원하는 데이터 형태(`Target Interface`)만 알고 있음.
2.  **Adaptee (외부 API)**: 제멋대로 생긴 데이터(`Incompatible Interface`)를 줌.
3.  **Adapter (변환기)**: 외부 데이터를 받아서 우리 앱이 원하는 형태로 뚝딱 변환해줌.

---

## 4. 실전 구현 코드 (TypeScript)

이 프로젝트(`realtime-crypto-dashboard`)에 실제로 적용된 코드입니다.

### 4.1 상황 설정

**외부 API (Binance)가 주는 데이터:**
```typescript
// 알아보기 힘든 축약어 사용
interface BinanceTicker {
  s: string; // Symbol
  c: string; // Current Price
  p: string; // Price Change
  v: string; // Volume
}
```

**우리 앱이 원하는 데이터 (Domain Model):**
```typescript
// 직관적이고 타입이 명확한 구조
interface Ticker {
  symbol: string;
  price: number;      // 문자열 -> 숫자 변환 필요
  priceChange: number;
  volume: number;
}
```

### 4.2 어댑터 구현 (`adapters/binance.ts`)

```typescript
export function adaptBinanceTicker(raw: BinanceTicker): Ticker {
  return {
    // 1. 필드명 매핑 (s -> symbol)
    symbol: raw.s,
    
    // 2. 타입 변환 (string -> number)
    price: parseFloat(raw.c),
    priceChange: parseFloat(raw.p),
    volume: parseFloat(raw.v),
    
    // 3. 추가 가공 (필요하다면)
    lastUpdated: Date.now()
  };
}
```

### 4.3 사용 예시

```typescript
// API 호출
const response = await fetch('https://api.binance.com/...');
const rawData = await response.json();

// ✨ 어댑터 통과! (여기서 변환됨)
const myTicker = adaptBinanceTicker(rawData);

// 이제 앱 내부에서는 깔끔한 myTicker만 사용
console.log(myTicker.price); // 50000 (숫자)
```

## 5. 프론트엔드 활용 사례

### 5.1 API 응답 정규화 (가장 흔함)
백엔드 개발자가 `user_name`, `userName`, `u_name` 등 API마다 필드명을 다르게 줘도, 프론트엔드 어댑터에서 `name`으로 통일시켜버리면 컴포넌트는 신경 쓸 필요가 없습니다.

### 5.2 레거시 코드 호환
오래된 라이브러리(jQuery 등)를 걷어내고 최신 라이브러리로 바꿀 때, 기존 코드를 다 뜯어고치는 대신 **새 라이브러리를 감싸는 어댑터**를 만들어서 기존 코드인 척 동작하게 할 수 있습니다.

### 5.3 여러 데이터 소스 통합
- 구글 지도 API
- 네이버 지도 API
- 카카오 지도 API

이 3가지 API는 사용법이 다 다릅니다. 하지만 `MapAdapter`라는 인터페이스를 정의하고 각각의 어댑터를 만들면, 우리 앱은 **"지도에 마커 찍어줘"**라는 하나의 명령으로 3가지 지도를 모두 제어할 수 있습니다.

## 6. 장점과 단점

### ✅ 장점
1.  **유지보수성**: 외부 API가 바뀌어도 어댑터 코드 한 줄만 고치면 끝납니다.
2.  **재사용성**: 비즈니스 로직이 특정 API에 종속되지 않습니다.
3.  **가독성**: 컴포넌트 코드에서 지저분한 데이터 변환 로직이 사라집니다.

### ❌ 단점
1.  **복잡도 증가**: 파일이 하나 더 늘어나고 코드가 조금 더 많아집니다.
2.  **오버헤드**: 아주 미세하지만 변환 과정에서 성능 비용이 발생합니다. (대부분 무시 가능)

## 7. 함께 알아두면 좋은 패턴들

어댑터 패턴과 비슷하지만 목적이 다른 **구조적 패턴(Structural Patterns)**들을 소개합니다.

### 7.1 퍼사드 패턴 (Facade Pattern)
**"복잡한 건 내가 다 감춰줄게, 너는 버튼 하나만 눌러."**

- **설명**: 복잡한 서브시스템(여러 개의 클래스나 API)을 감싸서, 사용하기 쉬운 **단순한 인터페이스**를 제공하는 패턴입니다.
- **언제 쓰나요?**:
  - 라이브러리 사용법이 너무 복잡해서 팀원들이 힘들어할 때.
  - `fetch` API의 복잡한 설정(헤더, 에러 처리 등)을 매번 반복하기 싫을 때.
- **예시**: `api.get('/users')` 한 줄로 복잡한 HTTP 통신을 처리하는 유틸리티 함수.

### 7.2 데코레이터 패턴 (Decorator Pattern)
**"기존 기능은 그대로 두고, 포장지만 예쁘게 씌워줄게."**

- **설명**: 객체의 코드를 변경하지 않고, 실행 시점에 **새로운 기능을 동적으로 추가**하는 패턴입니다.
- **언제 쓰나요?**:
  - 기존 컴포넌트를 수정하지 않고 로그 수집 기능을 붙이고 싶을 때.
  - 특정 함수 실행 전후에 권한 체크 로직을 넣고 싶을 때.
- **예시**: `@Log` 데코레이터를 붙여서 함수 실행 시간을 자동으로 기록하기.

### 7.3 프록시 패턴 (Proxy Pattern)
**"사장님 만나려면 비서인 나를 먼저 거쳐야 해."**

- **설명**: 원래 객체 대신 **대리인(Proxy)** 객체를 내세워서 접근을 제어하거나 부가 작업을 수행하는 패턴입니다. 인터페이스는 원래 객체와 똑같습니다.
- **언제 쓰나요?**:
  - **지연 로딩(Lazy Loading)**: 이미지가 화면에 보일 때까지 로딩을 미루고 싶을 때.
  - **캐싱(Caching)**: 똑같은 API 요청이 오면 서버에 안 가고 저장해둔 값을 주고 싶을 때.
  - **보안(Security)**: 관리자만 특정 함수를 실행할 수 있게 막고 싶을 때.
- **예시**: `React.memo` (props가 안 바뀌면 리렌더링을 막아주는 대리인 역할).

---

## 🎯 요약

1.  **어댑터 패턴**: 호환되지 않는 인터페이스를 연결해주는 **변환기**.
2.  **목적**: 외부 시스템(API)의 변경으로부터 우리 시스템(앱)을 보호하기 위함.
3.  **구현**: `Input(외부 데이터)` -> **[변환 로직]** -> `Output(내부 데이터)`
4.  **필수 역량**: API 의존성을 줄이고 견고한 프론트엔드 아키텍처를 설계하기 위한 필수 패턴.
